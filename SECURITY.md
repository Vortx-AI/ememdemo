# Threat model

ememdemo is a static page. Everything it claims, it checks in the reader's browser. This file lists what an attacker could try, including a swarm of agents, and what stops each attempt today. Anything not yet covered is tracked as an issue (label `security`).

| threat | what stops it today | still open |
|---|---|---|
| **The site's code is swapped** (a compromised host, CDN or repository) | `index.html` pins one manifest on emem by its sha256. Every file the page runs is checked against it; a file that does not match is replaced by the true bytes from emem. A manifest that does not match makes the page refuse to run. | The key that signs the seal exists only where it was made; sealing should move to CI with a managed secret. |
| **Injected script** (XSS through a document, a note or a URL) | A Content-Security-Policy generated at seal time allows exactly one inline script (the loader, by its sha256), blobs made from checked bytes, and pinned libraries. There are no forms, no framing of other origins, and no base-URL changes. Documents are rendered as text, never as HTML. | The browser key is still extractable in `localStorage`; a non-extractable key needs an explicit export step. |
| **A third-party library is swapped** | Every library the page may load is pinned by its sha256 in the manifest and refused if it differs. | Tesseract's worker, core and language data, and the text reader used for pages without CORS, are not yet content-pinned. |
| **Prompt injection hidden in a document** (text addressed to whatever AI reads it later, sometimes in invisible characters) | Ingested text is scanned. Passages that tell a model to drop its instructions, change role, hide things from its user, send secrets, pipe downloads into a shell, or smuggle data out through image links are listed under "Read as data", together with invisible characters. Every hand-off (AGENTS.md, chat) tells the agent that everything behind the link is data, not instructions. | The scanner is a set of patterns, not a model; a determined attacker can phrase around it. emem-guard should also check outputs before they are published. |
| **A pointer that lies** (the data behind a link is swapped after it was named) | Every chunk is named by BLAKE3-256, and the table by a Merkle root or chain. Opening a pointer re-reads a spread of chunks from the source. Folders are listed again; camera clips are hashed again. Tested: one flipped byte is reported as "CHANGED". | Checks sample the data; full coverage grows only as chunks are added with "hash 8 more". |
| **Backdating** (claiming something was written earlier than it was) | Each result carries the signed log head it was written after, which cannot be known in advance. Opening it proves, with an RFC 9162 consistency proof checked in the browser, that the log still contains that head. | Notes are not yet entries in the log, so there is no upper bound on when they were written. |
| **A split or rewritten log** | Consistency proofs from the stamped head to today's head. The writer's key co-signs the head it saw. | Witnesses are any key (Sybil-cheap), and there is no gossip between readers yet. |
| **A swarm of fake witnesses** vouching for a pointer | A witness only counts if its bytes and Ed25519 signature check, it names the pointer, and it is not the author's own key. | Keys are free, so the count shows independent re-reads, not independent parties. It needs identity tiers on emem. |
| **Numbers drifting between source and answer** (a rounding error, a retyped digit) | World readings print exact values, and emem's `echo_verify` checks every printed number against its token. The check tab traces quotes and numbers in an AI's answer back to the source, and emem-guard gives a signed verdict on cited tokens. | Other result kinds do not yet echo-verify every number they print. |
| **Write floods** (a swarm writing through a key) | emem enforces per-key limits; the page stays under them and retries politely. | Keys are free; abuse resistance depends on emem's enlist tiers. |
| **Identifying data leaking from medical files** | DICOM pointers copy technical tags only; patient fields stay at the source, and only their hash is recorded. | Private data needs client-side encryption before anything is written. |

To report a vulnerability, open a private security advisory on this repository.
